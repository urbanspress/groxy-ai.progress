## 1. Purpose, Scope & Approval Boundary

Help an operator design only the store tables they need, understand the consequences of proposed changes, and explicitly approve an exact database change after reviewing its impact. Target approval does not approve this specification or authorize implementation. No v1.5.0 code in `src/`, `views/`, `public/`, `assets/`, `tests/`, or `playbook/` may be written before explicit owner approval. Preserve untracked `playbook/genres/`, all frozen specifications and releases, and sibling repositories.

Three additive routes provide quiz planning, opt-in consultation, and approved apply. No automatic migration at startup, reload, quiz completion, or conversation time; `ADR-024f` migrations run explicitly in a controlled maintenance operation. Do not duplicate compiler, numeric, database-driver, Grex runtime, or SSH infrastructure. No checkout/payment processing, subscription billing, tax determination service, fulfillment execution, publication, or silent copy/template replacement is included. Business flags describe schema needs, not operational or regulatory authorization.

Use existing upstream capabilities only. A tunnel is transport, not a migration executor or approval boundary. If a destination cannot enforce this specification's locking, exact numeric storage, snapshot, maintenance, or receipt requirements, planning remains available but apply is blocked; report the missing capability for owner review rather than changing a frozen upstream or inventing an endpoint.

## 2. Shared Route, Context & Destination Contracts

All three POST routes require existing authenticated operator/site authorization and `X-CSRF-Token`; reject failures with `403` before inspection or staging. Resolve `target_id` from a server-side authorized registry binding site, database identity, adapter, and local workspace or pinned remote host. Never accept arbitrary DSNs, URLs, paths, SQL, shell commands, or credential material in requests. One plan targets one database; no distributed migration transaction is implied.

| Route | Request | Successful result / allowed side effects |
|---|---|---|
| `POST /api/groxy/db/architect-quiz` | `target_id`, structured `answers`, optional `generation_mode` | `200`: immutable migration proposal and dry-run diff; staging only |
| `POST /api/groxy/db/consult` | `target_id`, plain-English `question`, optional typed `proposed_change`, optional `generation_mode` | `200`: sourced answer and Impact & Risk Assessment; optional staged proposal; no database writes |
| `POST /api/groxy/db/apply` | `plan_id`, `target_id`, `migration_sha256`, `payload_sha256`, `approval_token`, `risk_acknowledged` | `201` only after verified execution and readback; `409` valid duplicate/replay |

Reject unknown fields, duplicate JSON keys, unsupported types, and invalid identifiers. `generation_mode` is `deterministic` by default, optionally `ollama` or `byok`. Read-only inspection uses least-privilege credentials and read-only transactions; mutation credentials are available only to the approved executor.

Live inspection combines `.grab` schema metadata via existing GRAB inspection capabilities, tables/columns/types/defaults/constraints/indexes, row counts, authorized order/inventory records, `slug_history` 301 redirects, and active `ForEach` Query Loop dependencies (selected fields, filters, sorting, joins, and bindings). Read `SITE-CONTEXT.md` and derive confined `storage/SCHEMA-CONTEXT.md` plus a structured revisioned companion from authorized observations. Store hashes/revisions, observation time, target identity, provenance, exact/estimated count flags, and coverage gaps. Local context cache writes are not permission to mutate the inspected database.

Cached context is evidence, not proof of current live state. Missing, stale, contradictory, or incomplete dependencies prevent a claim of Safe and block executable destructive plans. Never treat an estimated count or absent context entry as zero rows/dependencies. Read the minimum authorized data; expose aggregate counts and redacted evidence by default, not customer addresses, payment details, or entire order dumps.

## 3. Bespoke Store Schema Quiz

The semantic Grex JS wizard asks eight concise questions, showing relevant follow-ups only:

1. Physical SKUs, digital downloads/ebooks, subscriptions, or a combination?
2. Which product variants are needed, and which require inventory tracking?
3. Which currencies and exact currency scales are used?
4. Which operator-supplied tax rules/rates and tax-inclusive/exclusive price fields must be represented?
5. Are bundles needed, and which fixed/percentage discount tiers are authorized?
6. Are correctional-facility fulfillment flags or facility-specific restrictions needed?
7. Is white-label fulfillment needed, and which partner/product references must be stored?
8. Is this a new store or a change to an existing store, and which configured database is the target?

Each answer explains its schema effect. Unknown tax/fulfillment requirements remain unresolved; do not invent rates, eligibility rules, or legal assurances. Use deterministic versioned rules to select a minimal base catalog/order/order-line structure only where required, then add variants, inventory, digital-asset references, subscription metadata, currency/tax rules, bundle relations/discount tiers, or fulfillment flags only when selected. Digital-only stores must not gain physical stock/shipping tables by default; subscription metadata must not activate billing. Existing compatible tables are reused, never duplicated or replaced silently. List each proposed table/column with its business justification and omitted modules with reasons.

Generate a versioned explicit `.grab` migration plan using `ADR-024f`, including ordered operations, preconditions, constraints/indexes, exact numeric definitions, expected affected counts, and a before/after schema and data diff. The dry run validates against inspected metadata or an isolated disposable copy; it never runs DDL against the live target. Mark whether results are analytical or actually executed on an isolated copy. Destructive effects, lock/maintenance needs, unsupported operations, and rollback limitations are prominent.

A valid executable proposal returns `schema_version: "1.5.0"`, `plan_id: "dplan_<hex>"`, `target_id`, `origin: "architect-quiz"`, normalized answers, rule version, exact migration text, `migration_sha256`, full `payload_sha256`, assessment, source revisions, before/after diff, dispatch manifest, snapshot/restore requirements, `approval_required: true`, single-use `approval_token: "dtok_<hex>"`, and expiry. Incomplete or unsupported proposals return `apply_blockers` and no token. Preview generation never dispatches a migration.

## 4. Opt-In Consultant & Impact Assessments

`groxy_db_consultant_enabled` defaults to `false`, is scoped to the authorized site/operator configuration, and must be explicitly enabled through existing protected settings. `/consult` returns `403` while disabled; prompts cannot enable it. Disabling it invalidates outstanding consultant approvals, and `/apply` rechecks the setting for consultant-origin plans. Quiz access is independent and never silently enables ongoing inspection or a background consultant.

The consultant answers ordinary questions such as “Can I rename this product price field?” or “Can we remove the inventory table?” from the inspected evidence. Questions alone authorize no mutation. A typed `proposed_change` may stage allowlisted operations: create table, add/rename/drop column, add constraint/index, or narrowly scoped insert/update/delete with exact row identities and expected before-values. Generated plans must use supported GRAB migration/data capabilities; no freeform SQL console or model-generated executable code is accepted. Conflicts with human copy/templates remain blocked; those edits require the existing draft/Builder review workflows.

Every assessment contains `risk_level`, a plain-English summary, ordered findings (`rule_id`, evidence, affected object/loop/order/redirect references, counts and certainty), potential data loss, dependency breakage, alternatives, blockers, and recovery limitations. Choose the highest applicable severity deterministically:

| Risk | Required reasoning and behavior |
|---|---|
| **Safe** | Fully inspected additive change with no destructive conversion, no broken dependencies, and satisfied constraints; still requires explicit approval and snapshot. |
| **Caution** | Locking/performance impact, uncertain coverage, new constraints, backfills, or compatible changes requiring operational care. Unresolved coverage/constraint issues block apply. |
| **High-Risk Data Loss** | Dropping populated structures, narrowing precision, deleting/changing historical order values, or renaming/dropping fields referenced by active loops, redirects, foreign keys, or inventory/order relations. Display exact impact and require explicit high-risk acknowledgement; unresolved dependencies still block apply. |

For example, renaming `products.price` when a live `ForEach` selects it must identify the affected loop and block execution until a separately reviewed compatibility transition resolves the dependency. Dropping an order-line column must identify historical rows and lost meaning. Removing a slug must account for existing `slug_history` 301 destinations/chains; never silently delete redirect history. Snapshot availability and an acknowledgement cannot override unresolved breakage. Prefer additive replacement/backfill and staged retirement where possible; no automatic Builder rewrites or destructive cascades.

An informational answer has no approval token. An executable consultant proposal uses the same immutable envelope as the quiz with `origin: "consult"`, question, typed operations, evidence and assessment bound into the payload. Schema-neutral data changes still include a canonical ordered change artifact in `migration_sha256`; there is no unhashed data-only shortcut.

## 5. Exact Columns, Semantic UI & Offline Generation

`ADR-025c` applies from column definitions through storage, readback, JSON, previews, and hashes. Money, rates, weights, dimensions, and discounts use exact base-10 `GrabDecimal`; counts/quantities and numeric identifiers use `GrabInteger`. Preserve textual SKU identifiers as strings. Declare precision, scale, nullability, default, and constraints explicitly for each numeric column; prohibit FLOAT/REAL/DOUBLE or adapters that silently use binary floats. Use upstream exact mappings, including an exact SQLite representation; unsupported mappings block apply. No JavaScript `Number`/`parseFloat` conversion for domain numerics. Reject numeric JSON values in these fields, exponent notation, overflow, truncation, mixed-currency arithmetic, and unrepresentable scale changes with `422`. Never silently round a tax/discount result or convert existing float data without an independently reviewed exact conversion policy.

Pin fixtures such as `"19.90"` times `"2"` plus `"0.10"` equals `"39.90"`, and integer `"9007199254740993"`. Verify trailing-zero wire preservation and exact database round-trip. Numeric protocol limits may be bounded JSON integers; table row counts remain exact integer strings or explicitly labeled estimates.

Wizard, consultant, risk report, migration diff, approval, errors and recovery views use only `grex.elements.json` and supported semantic HTML5 mappings with active `--grex-*` tokens and `.grex-c-*` classes. Require `validateElementNode()`, `auditAccessibility()`, `divCount === 0`, `innerHTMLWriteCount === 0`, and Light/Dark text contrast `>= 4.5:1`. Provide labels, keyboard navigation, progress/status announcements, error association, heading order, visible focus, and dialog focus restoration. Render schema names, questions, and diffs as text; reject unsafe nodes/URLs, inline event handlers, raw HTML, `outerHTML`, `srcdoc`, CSS expressions, executable templates, and nesting beyond 24 levels. No framework or build bundler.

The full quiz and risk engine work offline with deterministic rules and zero API fees against local metadata/context. Use a verified local design-system token snapshot; lack of remote connectivity must not force a provider call. Offline cached remote evidence is explicitly stale and cannot authorize a live remote mutation. Refresh live target evidence before apply. Missing local token metadata blocks UI acceptance rather than inventing tokens.

Optional Ollama is opt-in at exactly `127.0.0.1:11434`; timeout, offline, malformed, or unsafe output falls back cleanly with `fallback_used` and reason. Optional HTTPS BYOK enrichment obeys default-deny `--allow-net` and `GRAB-E402`, rejects private/link-local/metadata destinations, DNS rebinding and disallowed redirects, and grants no broad loopback exception. Credentials use existing capability-gated secret storage and never appear in logs/exports. Models receive minimized redacted metadata, not live records or secrets. Enrichment may explain deterministic findings but cannot lower risk, change exact values, invent evidence, select targets, generate executable migrations, approve, or call apply.

## 6. Immutable Hashes & Approval Binding

Canonicalize the migration/change artifact to UTF-8 without BOM, LF line endings and one final newline before displaying and hashing it. For `.grab` migrations require canonical `grab format` output and `grab check` success; hash the exact displayed, stored, dispatched bytes. `migration_sha256` is SHA-256 of that artifact. Data-operation parameters are also included in the complete payload; no external mutable files or unchecked instructions may be referenced.

Compute `payload_sha256` over recursive canonical UTF-8 JSON: sort object keys at every depth by Unicode code-point order, preserve array order, exact string code points and decimal spellings, compact separators, deterministic escaping, no BOM/trailing newline. Reject duplicate keys, non-finite values and unsupported types. Never normalize Unicode or coerce numeric strings. Pin independent cross-language fixtures before acceptance.

The immutable payload covers plan/rule versions, plan identity/origin, authorized operator/site/target identity, quiz answers or consultant proposal, complete ordered migration/data operations and bytes, `migration_sha256`, source/before-state revisions, evidence/assessment, exact row selections and before-values, dry-run diff, high-risk acknowledgement requirement, dispatch manifest, and snapshot/restore policy. Exclude only the payload digest itself and issuance-only token/expiry/transport diagnostics. Store canonical bytes and recompute both hashes from staging at apply.

Issue a cryptographically random `dtok_<hex>` with at least 256 random bits, bound to `{ plan_id, migration_sha256 }` **and** `payload_sha256`, site/operator, target identity and origin. Persist only a secure verifier and immutable staging; expire after 15 minutes. Token possession is not approval: only the explicit **Approve & Apply Reviewed Database Change** action submits apply after displaying destination, diff, risks and recovery limits. High-risk approval additionally requires `risk_acknowledged: true` for the displayed bound assessment. Editing any reviewed content invalidates approval and requires restaging.

## 7. Apply, Snapshot, Dispatch & Recovery

Apply performs authorization/CSRF, feature-setting, token/expiry/binding, stored digest, risk acknowledgement, destination capability, and current source/target checks before mutation. Client-supplied execution content is forbidden; load only immutable staged content. Return `403` for invalid/mismatched auth, CSRF, token, digest, target or acknowledgement; `409` for valid replay/concurrent loser, stale evidence or incompatible destination; `422` invalid content; `413` oversized bodies; `503` unavailable required services before dispatch. Binding mismatches remain `403` even for consumed tokens.

Atomically compare-and-transition `staged` to `applying` and consume approval durably before snapshot or execution. Exactly one contender wins across workers/processes and restarts; an in-memory mutex is insufficient. Acquire target-wide maintenance/execution coordination, revalidate schema, selected rows and active loop/redirect dependencies under a protected consistent boundary, and reject intervening changes. Different approved plans cannot race on the same database. If the target cannot prevent changes between freshness checks, snapshot and mutation, block apply.

Capture an automatic **Pre-Mutation SHA-256 Snapshot** named `snap_db_*` before the first operation. Include consistent schema, affected data/constraints, migration ledger and recovery metadata; use a full consistent database backup when destructive DDL requires it. Verify snapshot durability, digest and target binding before execution. Missing storage, insufficient space, corruption, or snapshot failure means zero mutations. A fleet Pre-Deploy Snapshot may supplement but cannot replace this database snapshot. Display snapshot ID, digest, scope and restore limitations in receipts.

Dispatch through the authorized existing Groxy Desk/Gashboard executor over host-key-pinned loopback SSH tunnels, or the supported local GrabLab database maintenance path. Groxy Desk's existing `/api/db/mutate/plan` and `/api/db/mutate/apply` remain independently approval-gated; bind any downstream plan/digest into the reviewed manifest and keep downstream tokens server-side. Never substitute a Groxy token for a Desk token, create a changed downstream plan after approval, or bypass an upstream confirmation. If bridging cannot preserve the same reviewed bytes and approval semantics, block for capability review. Local CMS content creation still uses `create_entry_draft`; the CMS draft API is not a DDL endpoint. Any separately approved layout update still uses `POST /api/mcp/layout`, `actor: "groxy-ai"`, and reversible command-stack staging.

Execute explicit `ADR-024f` migrations through the existing GRAB runner with structured argv, never shell interpolation or runtime auto-migration. Use a bounded database transaction where supported. For nontransactional DDL require a verified maintenance/backup/restore execution path; otherwise block before dispatch. Journal intent and receipts durably, and verify final schema, exact affected values/counts and health/readiness before `201` with `status: "applied"`, both hashes, snapshot receipt and restoration guidance. Successful concurrent attempts yield exactly one `201` and all other valid contenders `409` with one snapshot/mutation execution.

Atomic token consumption is not a distributed transaction. After the winning claim, failures leave the token consumed. Return `502` with truthful `failed`, `partial`, or `uncertain` outcome and known receipts after downstream failure/timeout; never blindly retry or report success. Reconcile target state before any fresh approval; unresolved uncertain work blocks redispatch. Restoration is a new authenticated, explicitly approved operation through the existing restore capability, with freshness checks and protection for intervening human writes. Never automatically restore an old snapshot over later orders. Demonstrate snapshot restoration on isolated fixtures; do not promise universal lossless rollback.

## 8. Storage, Bounds & Audit Trail

Confine staging, context and journals to fixed runtime `storage/` paths under `GRAB-E401`, excluded from Git/release archives. Reject traversal, NUL, UNC, escaping symlinks and protected secret paths. Snapshot storage remains managed by the authorized executor, encrypted/access-controlled under existing capabilities; no public downloads or provider uploads. Logs contain safe identifiers, rule outcomes, hashes and execution status, never approval tokens, credentials or private row contents.

Limit request and staged payload to 1 MiB each, question to 4,000 characters, quiz to eight primary answers plus bounded typed follow-ups, plan to 100 operations, inspection page to 100 rows, data adjustment to 100 explicit row identities, and dependency inspection to 10,000 references. Cap identifier length at 63 ASCII letters/digits/underscores, beginning with a letter/underscore, subject to actual backend limits and reserved-name checks. No unbounded deletes or predicate-only mass updates. Provider calls time out within 30 seconds; read-only inspection within 30 seconds; apply preflight records a destination-supported execution deadline. Exceeded inspection limits yield incomplete coverage and blockers, never silently safe truncation. Large DDL effects remain visible even though individual row edits are bounded. Retention cleanup must not delete unresolved journals or the only recoverable snapshot; enforce quota preflight and expose operator-managed retention.
